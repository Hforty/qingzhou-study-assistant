# 云端开发与发布

本仓库是轻舟唯一开发来源。Windows 软件仍由用户安装使用；开发与测试全部在 GitHub 托管运行器上完成。

## 日常流程

1. 在 GitHub 创建功能或修复分支，在线修改文件并提交，或者由当前对话通过 GitHub 连接提交。
2. 创建 PR，Actions 自动运行核心测试、Windows 构建、桌面交互和覆盖升级回归。
3. 失败时打开 Actions 对应作业的日志，下载诊断 artifact；在云端提交修复。无需本地启动、编译或测试。
4. 合入 main 后，再次验证并生成安装包及版本草稿。到 Releases 查看并下载独立 EXE；确认发布说明后可将草稿正式发布。

## 工作流

- 核心测试：Ubuntu + Node.js 24，依赖使用 package-lock.json 锁定。
- 桌面验收：GitHub Windows 托管运行器，时区设为中国标准时间，使用隔离记录，构建与测试不访问用户电脑。
- 升级回归：固定运行时基线 ffaf81d0af50b02bc6e870b5277a9b98e16ee0ef（baseline/v1.0.5），在同一云端临时安装目录验证 1.0.5 → 1.0.6 覆盖安装、旧 v4 备份及失败保护。
- 当前版本为 1.0.6。已公开的版本不覆盖；新升级修改版本号及更新说明。旧草稿版本可由本版本的后续成功构建更新。
- 核心、桌面和升级检查全部成功后，生成 EXE artifact。main 成功时创建或更新 Releases 草稿并上传 EXE 及 SHA256SUMS.txt。
- 失败或成功均保留测试日志、截图、构建核对和升级摘要 14 天；安装包 artifacts 保留 30 天，正式发布包由 Releases 保存。

## 数据和权限

源码保持公开。不上传个人学习记录、备份、凭据或开发缓存。CI 学习记录都是生成的测试样本，安装使用时的本机记录不迁入 GitHub。

工作流默认 contents:read，仅发布作业使用 contents:write。PR 不运行发布作业，检出不保留凭据。使用 GitHub 内置 GITHUB_TOKEN，不需要用户提供个人 Token。

测试和生产安装包保留既定安装标识与数据目录；测试包使用独立标识 cn.qingzhou.study.verification.v105 和独立目录。

GitHub 的额外仓库设置、可见性与分支保护由仓库所有者在 Settings 中管理。建议 main 要求 PR 并要求“核心测试”和“Windows 桌面、安装与升级”成功后合并。
